# Architecture

This page describes only what exists in the code **today** (S12-R1). S03 added the domain tables, the functions that write and read them, and the releases seed. S04-R1 added the indexing path: `make ingest` stores versions and chunks for the S04 scope, and `make embed` stores one vector per distinct chunk text. S04-R2 added the answer path: `orgknow ask` embeds the question, finds the nearest chunk texts with an HNSW index, asks Claude for a structured answer that cites chunk ids, rejects any citation that wasn't retrieved, and prints the answer as JSON, with one Langfuse trace per ask. S05-R1 widened `make ingest` to the `full` scope: the docs pages of 3 SIGs, the website release records and the feature gates at every release 1.20 → 1.37, with a moved page or renamed gate kept as one document (later URLs and names become aliases), and `make reset-corpus` to rebuild from empty. S05-R2 added the date-scoped sources and the CHANGELOGs: every KEP in the 3 SIG folders and the governance docs, read at each release date plus `head`, each version dated by when its change was merged (a governance doc that moves stays one document); the blog posts dated from 1.20, one version per content change, starting at publication; and the 18 CHANGELOGs at the kubernetes lock head, chunked without their table of contents and download tables. S05-R3 made the chunk text final (no `{#id}` anchors or HTML comment blocks, HTML tables whole, oversize lists and pipe tables cut between items or rows, no download tables in any source), ended `make ingest` with a report whose fingerprint shows two ingests stored identical data, added `make ingest-report`, and embedded every distinct chunk text. S06-R1 added the eval harness: a golden-set loader with a label check against the database, retrieval metrics and answer checks AC1–AC3, and `make eval`, which runs every golden question through retrieval and one answer call, writes a results folder and rebuilds the ablation table. S07-R1 added lexical search (a `tsvector` column on `chunks`, generated by the database, with a GIN index; every content word of the question must match, ranked by `ts_rank_cd`), Reciprocal Rank Fusion (RRF), and `RETRIEVAL_MODE`: `dense` retrieves as before, `hybrid` fuses the 20 nearest texts and the 20 best full-text matches and keeps the best 10. Hybrid became the default when it passed the improvement rule against dense (`docs/evaluation.md`). Every dense search sets its HNSW search width (`HNSW_EF_SEARCH`, 100). `make eval-retrieval` scores retrieval alone from the stored question vectors, with no paid call. S08-R1 added `RETRIEVAL_MODE=rerank` (ADR-008): hybrid's whole fused pool (about 21 texts) is scored by a local cross-encoder, `BAAI/bge-reranker-base` at a pinned revision on CPU-only PyTorch, and the best 10 by that score are kept; the model loads once per command, and only in that mode. Rerank was the default from S08-T5, when it passed the improvement rule against hybrid (`docs/evaluation.md`), until S09-T8 made `authority` the default. S09-R1 added the query router (ADR-009: one Claude call sorts a question into CURRENT, HISTORY, CHANGE or WHY and copies the release or year it names; code turns that into a release window through the `releases` table), the eval's stored routes and `make eval-routes`, the stale-result rate, temporal accuracy and router accuracy, and `RETRIEVAL_MODE=temporal`: rerank, with both searches filtered by the route before their own top 20 (CURRENT keeps text a current version holds; HISTORY with a window keeps texts valid in it ±1 release; everything else is unfiltered). S09-R2 added `observed_lifecycle` (migration `0006`) and `make lifecycle`: each feature gate's stage at each release, as that release's own feature-gate reference gives it, rebuilt by `make ingest` after chunking. S09-T6 gave every retrieved hit, in every mode, its authority at the question's target release (the latest, or a HISTORY window's end): a tier by source type (1 docs pages and the feature-gate reference, 2 release records, 4 governance docs, 6 blog posts; a KEP 3 once one of its `kep.yaml` gates has an `observed_lifecycle` row up to that release or it claims `implemented`, else 5; a withdrawn, rejected or replaced KEP is a superseded proposal, with no tier), and a KEP's effective stage there (observed, else its claim, else unknown). The tier and stage reach the prompt and every citation, and AC1 requires a tier. S09-T7 added `RETRIEVAL_MODE=authority` (ADR-003 D4 as changed in S09-R2): temporal's pool, reranked whole, then reordered by the reranker's probability (sigmoid of its score) times a factor for the route's mode (`AUTHORITY_BOOST` 1.25 for a source that mode trusts, `AUTHORITY_DEMOTE` 0.8 for a weak one, 1 otherwise), before the top-10 cut; and authority-selection accuracy: over the CURRENT golden questions whose labeled documents span 2+ tiers, the share whose first labeled hit has the best label tier, printed with the CURRENT questions' MRR. S10-R1 added conflict detection (ADR-010): every answer carries `conflicts[]`. Code finds two kinds in stored facts before the answer call: `claim_mismatch` (a KEP's claimed stage, from its version valid at the target release, vs. the one stage its gates' rows give there) and `history_date` (a KEP history line's release date vs. the releases table, beyond `HISTORY_DATE_TOLERANCE_DAYS`). The answer model lists pairs of chunks whose texts disagree in the same call; code checks their ids on their own (a bad pair is dropped, never rejecting the answer) and resolves each pair by ADR-003 D6 (the chunk valid at the target release, else the lower tier, else unresolved). Retrieval is unchanged. S10-R2 added the prompt's settle line (`Settle conflicts at release 1.N.`, the target release, before the question), showed a KEP's latest milestone in its claim line and its `claim_mismatch` summary only when it is older than the target release, and scored conflicts against the conflict set (ADR-007 D4: the disagreements among each eval question's top-K hits, labeled before the runs, 4 of them seeds): its loader and side check, `make eval-conflicts` (free: the rule-found conflicts' precision and recall), and in `make eval` conflict precision and recall (overall, and split by rule/model or rule/texts) and AC4 (each seed surfaced or not), with `run.json` recording the conflict file and its hash. S11 added no code: corrective retrieval was tested in sitting probes and not adopted (ADR-011). S12-R1 scored AC5 and AC6 on every saved eval run (S12-T1: per CURRENT question, every citation valid at the latest release; per HISTORY question with a golden window, at least one citation inside it), and moved the ask pipeline (route, retrieve, rule-found conflicts, answer, and its trace) from `cli.py` into `pipeline.answer_question`, which `orgknow ask` and the new `POST /query` both call (S12-T2). The API builds its clients and loads the reranker once per process, and `make serve` runs it with uvicorn. It is updated as slices land. The planned pipeline (ingestion → retrieval → generation → eval) is described in `CLAUDE.md` and `docs/product-spec.md`.

The answer path, `answer_question` (`pipeline.py`), which `orgknow ask "<question>"` (`cli.py`) and `POST /query` (`api/app.py`) both call:

```
  question
     │  RETRIEVAL_MODE=temporal or authority: ClaudeRouter (retrieval/router.py) ──► Anthropic API
     │  → Route (mode + time scope) → temporal_plan: resolve_window over the releases table,
     │  then plan (retrieval/temporal.py) → a TemporalFilter; the route line goes to stderr
     ▼
  retrieve (retrieval/retrieve.py) ── VoyageEmbedder, input_type "query" ──► Voyage API
     │  RETRIEVAL_MODE=dense: search (db/retrieval.py), the RETRIEVAL_TOP_K (10) nearest texts
     │  by cosine distance, through the HNSW index at width HNSW_EF_SEARCH (100)
     │  RETRIEVAL_MODE=hybrid: RETRIEVAL_CANDIDATES (20) texts from each of search and
     │  search_lexical (every question word, by full-text rank); fuse (retrieval/fusion.py):
     │  RRF over the two lists (k = RRF_K, 60), the RETRIEVAL_TOP_K best
     │  RETRIEVAL_MODE=rerank: hybrid's whole fused pool (no top-K cut) → CrossEncoderReranker
     │  (retrieval/cross_encoder.py, loaded once by main) scores each (question, text) pair →
     │  rerank (retrieval/rerank.py): the RETRIEVAL_TOP_K best by score, ties in fused order
     │  RETRIEVAL_MODE=temporal: rerank, with the route's filter inside both searches (a text is
     │  kept when some version holding it passes), before each one's RETRIEVAL_CANDIDATES
     │  RETRIEVAL_MODE=authority: temporal's whole reranked pool (no top-K cut), its authority
     │  attached, then weigh (retrieval/authority.py): sorted by sigmoid(rerank score) × the
     │  route mode's factor (AUTHORITY_BOOST, AUTHORITY_DEMOTE or 1), rounded to 4 decimals, ties
     │  in rerank order; the RETRIEVAL_TOP_K best
     │  every mode: each text once, with every release window it was valid in, then
     │  attach_authority: its tier and a KEP's effective stage at the target release
     │  (retrieval/authority.py; one observed_lifecycle read for the KEP hits' gates)
     ▼
  rule_conflicts (generation/conflicts.py), at the hits' target release, no network call:
     │  claim_mismatch: each KEP hit's claim, from its version valid there (db/lifecycle.py
     │  kep_versions_at), vs. the one stage its gates' observed_lifecycle rows give
     │  history_date: a KEP line "YYYY-MM-DD: … v1.N … released" vs. the releases table,
     │  beyond HISTORY_DATE_TOLERANCE_DAYS (7)
     ▼
  answer (generation/generator.py) ── AnthropicGenerator, messages.parse ──► Anthropic API
     │  prompt (generation/prompt.py): one evidence block per hit, with its authority line
     │  (a KEP's claim, with its latest milestone only when older than the target release),
     │  then "Conflicts found by code:", then "Settle conflicts at release 1.N."
     │  validate (generation/validate.py): reject any cited id that wasn't retrieved;
     │  fill each citation in from its hit (title, section, windows, tier, stage, GitHub URL)
     │  model_conflicts (generation/conflicts.py): the pairs the model listed, checked on their
     │  own (a bad pair is dropped to the trace); pair_conflict resolves each by ADR-003 D6
     │  conflicts[]: the rule-found ones (on every path with hits), then the model's kept pairs
     ▼
  `orgknow ask`: the answer JSON on stdout; "tracing off", the route line and errors on stderr
  `POST /query`: the same JSON as a 200; an ask error a 502, an unreachable database a 503

  Langfuse (only in pipeline.py, only with both keys): one trace per ask or request, named `ask`,
  with retrieve (and in temporal and authority modes its route, window and filter; per hit its
  tier, and in authority mode its factor and weighted score), generate (with the conflicts
  and the dropped model pairs; when the answer call fails, the rule-found conflicts, S12-R1
  triage g) and validate under it; flushed before the command exits, or at the API's shutdown
```

The eval path, `make eval` / `make eval-smoke` (`python -m orgknow.eval run`, `eval/runner.py`):

```
  golden file (EVAL_GOLDEN_PATH) ── load_golden_file (eval/golden.py): validate, ADR-007
     │  check_labels (eval/golden.py, SQL in db/eval.py): resolve aliases, count each
     │  label's texts; any 0 stops the run
     │  conflict file (EVAL_CONFLICTS_PATH), when it exists: check_conflicts (eval/runner.py):
     │  load_conflict_file, check_sides (eval/conflicts.py); a side entry matching no text stops
     │  the run; a full run adds the file's new questions (c01, …) to the pool
     ▼
  question vectors (EVAL_VECTORS_DIR/<model>.json) ── only missing ones ──► Voyage API, 1 request
     │
     │  temporal and authority modes: question routes (EVAL_ROUTES_DIR/<ROUTER_MODEL>.json) ──
     │  only missing ones ──► ClaudeRouter, 1 call each, saved as each arrives
     │  document_tiers: each labeled document's tier at the latest release (its newest version;
     │  db/lifecycle.py newest_versions and observations)
     ▼  per question, in file order
  retrieve with the stored vector (and route) ─► rule_conflicts ─► answer
     ─► score_retrieval (eval/metrics.py), check_answer (eval/checks.py)
     │  an ask error becomes the row's `error`; no Langfuse trace
     ▼
  EVAL_RESULTS_DIR/<name>-<UTC time>/: run.json, questions.jsonl, summary.json
     │  (and conflict_questions.jsonl, the new questions' rows; summary.json scores every row's
     │  conflicts against the conflict set with score_conflicts, eval/conflicts.py)
     │  (summary.json also scores AC5 and AC6 per golden question: check_ac5, check_ac6
     │  in eval/checks.py, at the latest stored release; S12-T1)
     │  (name: --name, or RETRIEVAL_MODE by default; RETRIEVAL_MODE-smoke with --smoke)
     ▼
  write_table (eval/table.py): ablation.md, one row per (name, golden_sha256)
```

`make eval-retrieval` (`python -m orgknow.eval retrieval`) runs the same label check, then retrieves in `RETRIEVAL_MODE` for every answerable question from its stored vector, scores the hits and prints the mode, the 4 metric means, the stale-result rate and temporal accuracy over the hits (S09-T3), authority selection and the CURRENT questions' MRR (S09-T7), in temporal and authority modes the router line (router accuracy, the resolved windows that equal the golden ones, and how many questions got each plan; S09-T4), the rule-found conflicts (S10-T2: how many `claim_mismatch` and `history_date` conflicts, and the questions holding one), and the retrieve time's p50 and p95 per question (in rerank, temporal and authority modes, also the model's load time). Temporal and authority modes read each question's stored route. No Voyage or Anthropic call (a missing vector or route is an error), and it writes nothing: the free check before a paid run.

`make eval-conflicts` (`python -m orgknow.eval conflicts`, S10-T6) checks the conflict set (`EVAL_CONFLICTS_PATH`, default `eval/golden_set/conflicts-v0.yaml`; exit 1 when the file is missing): `load_conflict_file` validates it against the golden question ids, and `check_sides` counts the texts each side entry matches (any 0 stops it). It then retrieves in `RETRIEVAL_MODE` for every golden question and the set's new questions from their stored vectors and routes, finds each one's rule-found conflicts, and prints 4 lines: the set's counts, how many conflicts search retrieved (reachable), how many seeds it retrieved, and the rule-found conflicts' precision and recall over the reachable rule kinds. No Voyage or Anthropic call (a missing vector or route is an error), and it writes nothing.

`make eval-routes` (`python -m orgknow.eval routes`) routes every golden question with no stored route, one `ROUTER_MODEL` call each, saving each route as it arrives in `EVAL_ROUTES_DIR/<ROUTER_MODEL>.json` with the router prompt's hash (a file made with another prompt is an error), then prints how many it routed, the route time's p50 and p95, and the cost (ADR-009 D3). When the conflict file exists, its new questions are routed too, and those with no stored vector are embedded in one Voyage request (S10-T6).

`summary.json` reports, besides the metric means, the p95 latency (nearest rank over the questions' retrieve + answer times), the retrieve stage's own p95 (null in folders written before S08-T3, whose rows don't time it) and the mean cost per question (input and output tokens at `GENERATION_PRICE_*`, over the questions with usage). Since S09-T3 it also counts the stale hits of the CURRENT questions and the hits in the golden release window of the questions with one (`stale`, `temporal`; null for rows written before, whose hits don't record `current` and `release_windows`), and, in temporal and authority modes, router accuracy over the answerable rows with a route (`router`; null in other modes, S09-T4). Since S09-T7 each row records its labels' tiers (`label_tiers`, in label order) and the summary counts authority selection (`authority`; null when no CURRENT question's labels span 2 tiers, and for rows written before). Since S10-R1 each row records its `conflicts` (the rule-found ones even on an error row) and `checks.loser_only`, and the summary counts `conflicts_rule`, `conflicts_model` and `loser_only_answers` (null in older folders); the run's summary line ends with `Conflicts: N (R rule, M model), K loser-only answers.` Since S10-T6, with a conflict file, a full run also runs the set's new questions (their rows in `conflict_questions.jsonl`, so the golden rows don't change), `run.json` records `conflicts_path` and `conflicts_sha256`, and the summary adds, over the golden and new rows: `conflict_precision` (flags matching a conflict of their question ÷ flags; `conflict_precision_rule` and `conflict_precision_model` by who found them), `conflict_recall` (reachable conflicts matched ÷ reachable conflicts; `conflict_recall_rule` and `conflict_recall_texts` by kind), `conflict_unreachable`, `ac4` (seeds surfaced ÷ seeds whose question ran) and `ac4_seeds` (each seed's retrieved and surfaced); each null with no conflict file and in older folders. Since S12-T1 the summary adds `ac5` and `ac6` (pass / total over the answerable CURRENT golden questions, and over the answerable HISTORY ones with a golden window; null when no such question ran) and `latest_release` (the latest stored release AC5 read, "1.37"); the summary line shows AC5 and AC6 after AC3. The conflict counts read the new rows too; every other field reads the golden rows only. The summary line then ends with `Conflict precision P (a of b), recall R (c of d reachable), AC4 s of n (q08: not retrieved).`, and a `Conflict questions: N (c01 c02), E errors, cost $X.` line follows it. `make eval-resummarize` (`python -m orgknow.eval resummarize`) rebuilds every folder's `summary.json` from its `questions.jsonl`, keeping its name, golden hash, start time, authority selection (which needs the golden labels, not in the rows), conflict counts and conflict metrics (which need the conflict set), so older folders gain the other fields; AC5 and AC6 are scored again from the golden file (a folder that ran another golden file keeps its own); it writes nothing else, and `make eval-table` then shows them.

## Components

| Path | What it does |
|---|---|
| `src/orgknow/settings.py` | `Settings` (pydantic-settings) reads `DATABASE_URL` (required, plain `postgresql://` form), `DB_CONNECT_TIMEOUT_S`, the corpus paths (`CORPUS_MANIFEST_PATH`, `CORPUS_LOCK_PATH`, `CORPUS_CACHE_DIR`), `INGEST_SCOPE` (default `full`), `CLAIM_SYNONYMS`, `CHUNK_MAX_TOKENS` (512), the embedding settings (`VOYAGE_API_KEY`, `VOYAGE_API_URL`, `EMBEDDING_MODEL`, batch and per-run token limits), the retrieval settings (`RETRIEVAL_TOP_K` 10, at most 40; `RETRIEVAL_MODE` `dense`, `hybrid`, `rerank`, `temporal` or `authority`, default `authority` since S09-T8's eval (`rerank` from S08-T5's, `hybrid` from S07-T4's); `RETRIEVAL_CANDIDATES` 20; `RRF_K` 60; `HNSW_EF_SEARCH` 100, which must be at least `RETRIEVAL_TOP_K` and `RETRIEVAL_CANDIDATES`; `RERANK_MODEL` `BAAI/bge-reranker-base`, `RERANK_REVISION` its pinned commit, `RERANK_MAX_LENGTH` 512 (1–512), `RERANK_BATCH_SIZE` 8 (1–256); `HISTORY_WINDOW_SLACK` 1 (0–5), temporal mode's widening of a HISTORY window; `AUTHORITY_BOOST` 1.25 (1–4) and `AUTHORITY_DEMOTE` 0.8 (above 0, at most 1), authority mode's weights), the generation settings (`GENERATION_MODEL` `claude-opus-5-5`, `GENERATION_EFFORT` `medium`, `GENERATION_MAX_TOKENS` 16,000, `ANTHROPIC_API_KEY`; `GENERATION_PRICE_INPUT_USD_PER_MTOK` 4.0 and `GENERATION_PRICE_OUTPUT_USD_PER_MTOK` 20.0, ADR-006 D1's prices, for the eval's cost per question), the router settings (`ROUTER_MODEL` `claude-opus-5-5`, `ROUTER_EFFORT` `low`, `ROUTER_MAX_TOKENS` 4,096, and `ROUTER_PRICE_*` for `make eval-routes`'s cost; ADR-009 D1), the tracing settings (`LANGFUSE_PUBLIC_KEY`, `LANGFUSE_SECRET_KEY`, `LANGFUSE_BASE_URL`) and the eval paths (`EVAL_GOLDEN_PATH`, `EVAL_CONFLICTS_PATH`, `EVAL_RESULTS_DIR`, `EVAL_VECTORS_DIR`, `EVAL_ROUTES_DIR`) from the environment, falling back to `.env`. Keys are `SecretStr`. It is built inside factories, never at import time. |

The lifespan builds what wasn't injected once, before the first request: the Anthropic client, generator and (temporal and authority modes) router, the Voyage embedder, the reranker (`load_reranker`; rerank, temporal and authority modes) and the Langfuse client (`langfuse_client`: "tracing off" once without keys); a missing Anthropic or Voyage key stops startup with a message naming the variable, never its value. Langfuse flushes at shutdown. Both routes are plain `def`, so FastAPI runs their blocking calls in a worker thread. Known limit: concurrent requests share the one reranker. |
| `src/orgknow/db/health.py` | `is_reachable()` opens a fresh psycopg connection with a timeout and runs `SELECT 1`. |
| `src/orgknow/db/url.py` | `with_psycopg_driver()` rewrites `postgresql://` to `postgresql+psycopg://`, the form SQLAlchemy needs. Only Alembic uses it. |

| `src/orgknow/eval/__main__.py` | `python -m orgknow.eval check \| sections \| run \| retrieval \| conflicts \| routes \| table \| resummarize` (the `eval-*` Make targets). `run` needs `ANTHROPIC_API_KEY`, and `VOYAGE_API_KEY` only when a vector is missing; in temporal and authority modes it also builds a `ClaudeRouter` for the missing routes; its `--name` defaults to `RETRIEVAL_MODE` (`<mode>-smoke` with `--smoke`, so smoke runs get their own table row). `retrieval` needs no key, prints the authority line in every mode and the router line in temporal and authority modes. `conflicts` needs no key and exits 1 with no conflict file. `routes` needs `ANTHROPIC_API_KEY` only when a route is missing, and, with a conflict file, routes its new questions too and embeds those with no vector (`VOYAGE_API_KEY` only then). In rerank, temporal and authority modes, `run`, `retrieval` and `conflicts` load the reranker once, before the question loop, and time the load. `resummarize` reads the golden file (its labels checked as `run` checks them) and the latest stored release, for AC5 and AC6 (S12-T1). Errors print one stderr line and exit 1. |

Every data-access function takes a `psycopg.Connection` and leaves the transaction to the caller (ADR-005). `src/orgknow/db/` is the only place with SQL, and every query is a fixed string with parameters.

There are two entry points. The API server: `make serve` runs `uv run uvicorn --factory orgknow.api.app:create_app --host 127.0.0.1 --port 8000` (uvicorn, ADR-004's 2026-10-12 amendment), and FastAPI's built-in `/docs` page lists the endpoints. The command line: the `orgknow` console script (`[project.scripts]` in `pyproject.toml`). Both answer through `pipeline.answer_question`.

## Database

`compose.yaml` runs one service: the pinned `pgvector/pgvector:0.8.1-pg18` image (ADR-004), published on `127.0.0.1:5433`. Data lives in the named volume `pgdata`, so it survives `make down`. A `pg_isready` healthcheck over TCP lets `make up` block until the database accepts connections.

The schema is specified in `docs/domain-model.md`:

| Table | Holds | Key rules |
|---|---|---|
| `releases` | One row per minor release (key `minor`, 24 = v1.24), seeded from the manifest | version matches minor; end of life after release |
| `documents` | One stable identity per document (`canonical_id`, `source_type`) | unique id with a known prefix; known source type |
| `document_aliases` | Old URLs and gate names pointing at a document | unique; never equal to a `canonical_id` (code check) |
| `document_versions` | One row per content change, with a release window and a date window | date windows of one document never overlap (`EXCLUDE … tstzrange … WITH &&`), so at most one is open |
| `chunks` | The embedded text of each version, by position, and its `search_vector` (generated by the database) | unique position per version; deleted with their version |
| `embeddings` | One `vector(1024)` per distinct chunk text per model (key `(content_hash, model)`); the table is the embedding cache | exactly 1024 numbers; well-formed hash; vectors no chunk uses are deleted by `make embed` |
| `observed_lifecycle` | One row per feature gate × release (key `(gate, release)`): the gate's stage as that release's own reference gives it, and `status_confidence` (S09-T5, migration `0006`); rebuilt whole by `make lifecycle` and `make ingest` | the release is a `releases` row; confidence high or low; a high row's stage is alpha, beta, stable or deprecated |

`embeddings.embedding` has an HNSW index for cosine distance (`0004`). On 20 real queries it returned the same top 10 as an exact scan (200 of 200); at the search width 100, 20 candidates matched an exact scan on all 43 golden questions (S07-R1). `chunks.search_vector` has a GIN index for full-text matches (`0005`).

After `make seed`, `make ingest` and `make embed` on the S04 scope, the dev database held 44 documents (43 docs pages, KEP-2579), 220 versions, 4,967 chunks with 1,583 distinct texts, and 1,583 `voyage-4-large` vectors. After `make reset-corpus && make ingest` on the `full` scope (S05-R1), it held 564 documents (64 docs pages, 8 release records, 491 feature-gate documents, KEP-2579), 1,332 versions, 9 aliases and 10,509 chunks. After S05-R2 it held 1,168 documents (64 docs pages, 26 release records of which 18 are CHANGELOGs, 491 feature-gate documents, 141 KEPs, 29 governance docs, 417 blog posts), 2,882 versions, 21 aliases and 48,194 chunks (20,499 distinct texts). After S05-R3's chunker changes it holds the same documents, versions and aliases, and 48,273 chunks with 21,552 distinct texts, each with one `voyage-4-large` vector (21,552 vectors). A from-empty ingest takes about 1.5 minutes; the full embed took 3 min 44 s.

## Verification loop

| Where | What runs |
|---|---|
| Every commit | pre-commit: `ruff check --fix` and `ruff format` |
| `make check` | ruff format check, ruff lint, `mypy --strict` on `src/`, unit tests |
| `make test-int` | migrates the test database, then runs the integration tests against it |
| CI (`.github/workflows/ci.yml`) | `check` job: `make check`. `integration` job: the same pgvector image as a service container, `make migrate` twice (the second run must be a no-op), a round trip down to `0001` and back up, then `make test-int` with `TEST_DATABASE_URL` set to the service database. |

CI calls the same Make targets as local development, and `UV_LOCKED=1` makes it fail if `uv.lock` is out of date. CI never runs `make seed`: tests seed what they need inside their own transaction.
